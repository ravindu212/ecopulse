======================================================================
2. PRODUCT VISION
======================================================================

Working product name:
EcoPulse

Tagline:
Understand your impact. Take action. Track change.

Core idea:
EcoPulse is a personal climate action platform for students and young adults. It helps users understand their everyday climate-related habits, identifies the areas where improvement is most useful, recommends practical actions, and tracks progress over time.

Primary audience:
- Students.
- Young adults.
- Approximately ages 15 to 30.
- Users who care about climate change but need practical, understandable actions.

Core product loop:
ASSESS -> UNDERSTAND -> ACT -> COMPLETE -> TRACK -> IMPROVE -> REPEAT

User promise:
The app will not merely tell users that climate change exists. It will help them decide what to do next.

======================================================================
3. PROBLEM STATEMENT
======================================================================

Many people understand that climate change is important but struggle to convert awareness into practical behavior.

Typical problems:
- Climate information is often broad or overwhelming.
- Users do not know which everyday habits matter most for them.
- Advice is generic instead of personalized.
- There is little feedback after an action is completed.
- Progress is difficult to visualize.
- Climate action can feel abstract and unrewarding.

EcoPulse solves this by:
- Asking a short lifestyle assessment.
- Producing a transparent Climate Action Score.
- Showing category strengths and weaknesses.
- Recommending practical actions.
- Letting users complete actions.
- Tracking estimated impact, XP, streaks, and progress.
- Offering short climate challenges.

8. DOMAIN MODEL / DATABASE DESIGN
======================================================================

Use UUID primary keys unless a strong implementation reason suggests otherwise.
Use UTC timestamps in storage.

TABLE: users

Fields:
- id: UUID primary key
- name: string, required
- email: string, unique, indexed, required
- password_hash: string, required
- xp: integer, default 0
- current_streak: integer, default 0
- longest_streak: integer, default 0
- last_action_date: date nullable
- created_at: timestamp
- updated_at: timestamp

Do NOT store:
- plaintext passwords.
- derived dashboard totals that can easily be calculated, unless performance later justifies it.

TABLE: assessments

Fields:
- id: UUID primary key
- user_id: foreign key -> users.id
- answers: JSONB
- transport_score: integer 0..100
- energy_score: integer 0..100
- food_score: integer 0..100
- waste_score: integer 0..100
- overall_score: integer 0..100
- lowest_category: enum/string
- created_at: timestamp

Reason for JSONB:
The assessment is small and evolving. JSONB keeps the first version flexible while category/overall scores remain queryable columns.

TABLE: climate_actions

Fields:
- id: UUID primary key
- title: string
- slug: string unique
- category: enum/string [transport, energy, food, waste]
- description: text
- why_it_matters: text nullable
- difficulty: enum [easy, medium, hard]
- impact_level: enum [low, medium, high]
- estimated_co2e_kg: decimal nullable
- xp_reward: integer
- recommendation_tags: JSONB or array
- active: boolean default true
- created_at
- updated_at

Important:
estimated_co2e_kg is an estimate used only when a reasonable estimate is available.
UI must label it as estimated.

TABLE: user_actions

Fields:
- id: UUID primary key
- user_id: FK -> users
- action_id: FK -> climate_actions
- status: enum [started, completed, cancelled]
- started_at: timestamp
- completed_at: timestamp nullable
- xp_awarded: integer default 0
- estimated_co2e_kg_awarded: decimal default 0
- created_at
- updated_at

Rules:
- XP is awarded only once per completion record.
- Avoid accidental double-completion.
- For repeatable actions, create a new user_action record rather than re-awarding the same one unless a repeat model is explicitly implemented.

TABLE: challenges

Fields:
- id: UUID primary key
- title: string
- slug: string unique
- description: text
- category: nullable
- duration_days: integer
- xp_reward: integer
- badge_name: nullable
- active: boolean
- created_at
- updated_at

TABLE: challenge_actions

Fields:
- id: UUID primary key
- challenge_id: FK -> challenges
- action_id: FK -> climate_actions
- day_number: integer nullable
- sort_order: integer

TABLE: user_challenges

Fields:
- id: UUID primary key
- user_id: FK -> users
- challenge_id: FK -> challenges
- started_at: timestamp
- completed_at: timestamp nullable
- status: enum [active, completed, abandoned]
- completed_steps: integer default 0
- created_at
- updated_at

OPTIONAL TABLE: badges
Only add if badges are actually implemented.

Indexes:
- users.email
- assessments.user_id + created_at
- climate_actions.category
- user_actions.user_id + created_at
- user_actions.user_id + status
- user_challenges.user_id + status

Relationships:
User 1 -> many Assessments
User 1 -> many UserActions
ClimateAction 1 -> many UserActions
Challenge many <-> many ClimateAction through ChallengeAction
User many <-> many Challenge through UserChallenge

9. AUTHENTICATION AND SECURITY
======================================================================

MVP authentication:
- Email + password.
- Backend owns authentication.
- Password hash using Argon2 through pwdlib.
- JWT access token.
- Frontend sends Authorization: Bearer <token>.

Practical project decision:
For the short competition build, token persistence may use sessionStorage or a carefully isolated client-side auth store.
Do NOT claim this is the ideal production design.
If time permits, improve to a secure cookie/proxy strategy later.

Backend endpoints:
POST /api/v1/auth/register
POST /api/v1/auth/login
GET  /api/v1/auth/me

Register validation:
- valid email
- reasonable name length
- password minimum length
- duplicate email rejected

Login:
- generic invalid credentials error
- never reveal whether password or email was specifically wrong

Authorization:
- All /me, assessments, user actions, challenges join/progress, and progress endpoints require a valid token.
- A user may only mutate their own records.

CORS:
Development:
- allow http://localhost:3000

Production:
- allow only deployed frontend origin(s)
- do not use wildcard origins with credentials-sensitive behavior

Secrets:
- JWT secret from environment
- DB connection string from environment
- never hardcode credentials

Error handling:
- predictable JSON errors
- no stack trace returned to client in production

10. CLIMATE ASSESSMENT DESIGN
======================================================================

Goal:
Create a useful personalized score without pretending to be a scientific carbon footprint calculator.

Important language:
Call it a "Climate Action Score" or "Lifestyle Climate Score".
Do not call it an exact carbon footprint unless a validated emissions methodology is later implemented.

Higher score = more climate-friendly current habits.

Category score range:
0 to 100.

Overall score:
Average of the four category scores for MVP:
overall = round((transport + energy + food + waste) / 4)

Keep weights equal initially.
This makes the scoring model easy to explain and avoids pretending arbitrary category weighting is scientifically authoritative.

Assessment target length:
12 to 16 questions total.
Aim for about 3 minutes.

Example questions:

TRANSPORT
T1. What is your most common travel mode?
- walk/cycle -> 100
- train -> 85
- bus -> 75
- shared car/ride -> 55
- motorcycle -> 40
- private car -> 25

T2. How often do you choose walking/cycling for short trips?
- almost always -> 100
- often -> 80
- sometimes -> 60
- rarely -> 30
- never -> 10

T3. How often do you use public transport when practical?
- almost always -> 100
- often -> 80
- sometimes -> 60
- rarely -> 30
- never -> 10

ENERGY
E1. Do you turn off lights/devices when not needed?
- always -> 100
- usually -> 80
- sometimes -> 55
- rarely -> 25

E2. How often do you use air conditioning for long periods?
- rarely/never -> 100
- occasionally -> 75
- several days/week -> 45
- daily for long periods -> 20

E3. Do you intentionally use energy-saving settings/appliances?
- frequently -> 100
- sometimes -> 65
- rarely -> 30
- not sure -> 50

FOOD
F1. How often do you eat high-impact meat meals?
Use neutral wording and no moral judgment.
- rarely -> 100
- 1 to 2 times/week -> 80
- 3 to 4 -> 55
- most days -> 30

F2. How often is food thrown away in your household/personal meals?
- almost never -> 100
- occasionally -> 75
- sometimes -> 50
- often -> 20

F3. Do you intentionally choose local/seasonal or lower-waste food options?
- often -> 100
- sometimes -> 65
- rarely -> 30

WASTE
W1. How often do you use reusable bottles/bags/containers?
- almost always -> 100
- often -> 80
- sometimes -> 55
- rarely -> 25

W2. Do you separate recyclable waste where facilities are available?
- consistently -> 100
- sometimes -> 60
- rarely -> 25
- facilities unavailable -> neutral 50

W3. How often do you avoid unnecessary single-use items?
- almost always -> 100
- often -> 80
- sometimes -> 55
- rarely -> 25

Scoring:
- Each question maps to a numeric value.
- Category score = rounded mean of its question scores.
- Overall = rounded mean of category scores.
- lowest_category = lowest category score.
- If tied, choose based on a deterministic order or return multiple weak categories.

Important:
Store the scoring rules in backend code/config, not frontend.
Frontend should not be able to manipulate the final score.

11. RECOMMENDATION ENGINE
======================================================================

MVP recommendation engine is deterministic and rule-based.

Inputs:
- latest assessment category scores
- relevant answers
- user's already completed/recent actions

Priority:
1. Lowest category.
2. Second-lowest category.
3. Actions matching problematic answers.
4. Prefer actions not recently completed.
5. Mix difficulty so at least one easy action appears.

Example:
If transport is the lowest category and user says private car:
Recommend:
- Replace one short car trip with walking/cycling.
- Use public transport for one trip this week.
- Combine errands into one journey.

If waste score is low:
Recommend:
- Use a reusable bottle today.
- Refuse one unnecessary single-use item.
- Separate recyclable waste this week.

API response should return:
- action id
- title
- category
- difficulty
- impact level
- XP
- estimated impact if available
- short reason such as "Recommended because transport is currently your lowest category."

Do not use AI for MVP recommendations.
Rule-based logic is more reliable, explainable, testable, and faster to finish.

======================================================================
12. XP, STREAK, AND PROGRESS RULES
======================================================================

XP:
Each climate action has an xp_reward.

Suggested:
Easy: 40 to 60 XP
Medium: 70 to 100 XP
Hard: 120 to 160 XP

Do not calculate XP in frontend.

On completion:
- validate ownership and state
- mark action completed
- set completed_at
- award XP exactly once
- add estimated CO2e value exactly once if present
- update streak
- check challenge progress

STREAK:
Simple daily streak based on at least one completed climate action per calendar day.

Rules:
- If no last_action_date: streak = 1.
- If last_action_date is yesterday: streak += 1.
- If last_action_date is today: streak unchanged.
- Otherwise: streak = 1.
- longest_streak = max(longest_streak, current_streak)
- update last_action_date

Be explicit about timezone handling.
For MVP, use UTC consistently or a clearly documented application timezone.
Do not let repeated actions on the same day increase streak multiple times.

Estimated impact:
Dashboard sum:
SUM(user_actions.estimated_co2e_kg_awarded WHERE status=completed)

Always display:
"Estimated CO2e avoided"
not
"CO2 definitely saved"

13. CHALLENGE LOGIC
======================================================================

MVP:
Challenges are curated by seed data.

Example challenge:
7-Day Low Carbon Starter

Challenge actions:
Day 1: Use a reusable bottle.
Day 2: Walk/cycle one short journey.
Day 3: Avoid one single-use plastic item.
Day 4: Turn off unused devices.
Day 5: Choose a lower-impact meal.
Day 6: Use public transport where practical.
Day 7: Complete one action of your choice.

Joining:
POST /challenges/{id}/join

Progress:
- challenge step completion should be derived from relevant user action completions where practical
OR
- explicit challenge step completion may be implemented if it is simpler and clearly connected to backend.

Completion:
- all required steps completed
- award challenge XP once
- set completed_at
- badge can be shown if enabled

Avoid complex recurring scheduling for MVP.

25. BACKEND IMPLEMENTATION CONVENTIONS
======================================================================

FastAPI:
- prefix routes with /api/v1
- use APIRouter
- keep endpoints thin
- move business rules to services
- Pydantic schemas separate from ORM models
- use dependency for DB session
- use dependency for current authenticated user
- keep config in pydantic-settings
- use SQLAlchemy 2-style code

Example responsibility split:

route:
- parse request
- call service
- return response

service:
- business rules
- database operations
- score calculations
- XP rules

model:
- persistence definition

schema:
- request/response validation

Avoid:
- giant main.py
- SQL in route functions
- password logic in frontend
- duplicated scoring logic
- global mutable DB session
- broad except Exception that hides bugs

26. FRONTEND IMPLEMENTATION CONVENTIONS
======================================================================

Next.js App Router.

Rules:
- TypeScript strict.
- Small composable components.
- Do not put the entire dashboard in one component.
- Centralize API base URL.
- Centralize auth token handling.
- Use consistent loading/error components.
- Avoid unnecessary global state.
- Server Components may be used for static/marketing content.
- Authenticated interactive screens can use client components where practical.
- Keep form validation readable.
- Use semantic HTML.
- Keep route paths consistent.

API helper:
Create src/lib/api.ts.

Responsibilities:
- build URL
- attach Authorization header when token exists
- parse JSON
- throw normalized errors

Do not scatter fetch boilerplate across every component if avoidable.
